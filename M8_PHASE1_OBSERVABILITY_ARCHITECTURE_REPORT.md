## 3. Privacy Telemetry Policy & Governance

Every operational signal, metric, log, and diagnostic event generated by Islam Ul Haramain must be classified under one of three strict governance tiers:

```text
┌─────────────────────────────────────────────────────────────────────────────┐
│                       TELEMETRY PRIVACY CLASSIFICATION                      │
├──────────────────────────────┬──────────────────────────────────────────────┤
│ 1. ALLOWED                   │ Strictly operational, non-PII, system-level  │
│                              │ metrics required for platform availability.  │
├──────────────────────────────┼──────────────────────────────────────────────┤
│ 2. ALLOWED AFTER             │ High-level operational events containing     │
│    SANITIZATION              │ context that must be stripped of route params│
│                              │ and user identifiers prior to processing.    │
├──────────────────────────────┼──────────────────────────────────────────────┤
│ 3. PROHIBITED                │ Non-negotiable ban: Religious interactions,  │
│                              │ precise GPS, auth tokens, personal notes.    │
└──────────────────────────────┴──────────────────────────────────────────────┘
```

### Core Privacy Principles
1. **Zero Devotional Surveillance:** An individual's worship, Quran recitation, Hadith study, and personal supplications are sacred and confidential between the worshipper and Allah. The platform shall never track what an identifiable person reads, recites, searches, or saves.
2. **Coarse Location Only:** Prayer times and Qibla bearings require geographical parameters. Precise GPS coordinates (latitude, longitude, altitude) must remain strictly on the user's local client device. Any server-side prayer calculation requests must accept only coarse, rounded approximations or preset city identifiers.
3. **Data Minimization by Default:** Only the minimum data necessary to detect, isolate, and remediate technical errors or platform outages is collected.
4. **No Untyped Metadata:** Escape hatches such as `Record<string, unknown>` or free-form key-value blobs are architecturally forbidden in telemetry schemas.

## 8. Structured Logging Standard

All platform services (Next.js server runtime, background sync workers, Edge functions) shall output single-line newline-delimited JSON (NDJSON) to `stdout`/`stderr`.

### Log Level Taxonomy

```text
FATAL ──► System unusable, catastrophic crash, DB corruption, data-loss risk. Immediate pager alert.
ERROR ──► Request failed, unhandled exception, critical dependency outage. On-call alert.
WARN  ──► Degraded performance, retryable network failure, deprecated client version.
INFO  ──► Normal operational milestones (startup, graceful shutdown, schema migration, sync complete).
DEBUG ──► Detailed diagnostics, internal state transitions (strictly disabled in production).
```

### Structured Log Record Format

Prior to serialization, every log record must pass through an automated regex and key-name scrubber:

## 9. Correlation-ID Contract

Distributed tracing requires tracking requests across client, edge, server, and database tiers without establishing an attack vector for request spoofing.

### Header Standards
- **`X-Correlation-ID`:** End-to-end workflow identifier spanning multiple HTTP hops (e.g. Flutter client sync mutation $\to$ Next.js route $\to$ Supabase database mutation).
- **`X-Request-ID`:** Single-hop transaction identifier generated by the edge proxy or web server for a single HTTP transaction.

### Correlation Governance & Trust Boundaries
```text
┌─────────────────────────────────────────────────────────────────────────────┐
│                       CORRELATION-ID TRUST BOUNDARY                         │
└──────────────────────────────────────┬──────────────────────────────────────┘
                                       │
                         Untrusted Inbound HTTP Request
                                       │
                                       ▼
                       ┌───────────────────────────────┐
                       │ Does X-Correlation-ID exist?  │
                       └───────┬───────────────┬───────┘
                               │ YES           │ NO
                               ▼               ▼
                 ┌───────────────────────────┐   ┌───────────────────────────┐
                 │ Validate Format:          │   │ Generate fresh cryptosecure│
                 │ Regex: ^[a-zA-Z0-9_-]{16,64}$│ │ UUID v4.                  │
                 └─────┬───────────────┬─────┘   └─────────────┬─────────────┘
                       │ VALID         │ INVALID               │
                       ▼               ▼                       │
             ┌───────────────────┐ ┌───────────────────────┐   │
             │ Accept & Propagate│ │ Discard invalid input;│   │
             │ downstream        │ │ Generate fresh UUID.  │   │
             └─────────┬─────────┘ └───────────┬───────────┘   │
                       │                       │               │
                       └───────────────────────┼───────────────┘
                                               ▼
                                 Attach X-Correlation-ID
                                 to all logs & responses
```

1. **Client Generation:** Mobile apps and web browsers may generate an `X-Correlation-ID` using UUID v4 for tracking initial user actions.
2. **Server Validation:** The Next.js API server checks inbound headers against `^[a-zA-Z0-9_-]{16,64}$`. Any header failing validation (e.g. containing SQL, injection payloads, or exceeding 64 chars) is silently dropped and replaced with a fresh UUID v4.
3. **Audit Log Linkage:** When an authenticated administrative mutation occurs, the validated `correlation_id` is written directly into `public.audit_logs.correlation_id` in Supabase.
4. **Response Reflection:** The final HTTP response header MUST return the validated `X-Correlation-ID` to allow client-side troubleshooting.

## 10. Web Request Tracing Contract

In Next.js, request tracing operates along the ingress pipeline:

```text
Browser / Mobile Client
       │
       ▼ [Inbound HTTP: Optional X-Correlation-ID]

       │ 3. Attaches correlationId to Supabase DB query tags

       │ (Records correlation_id in audit_logs if admin action)
       ▼
Response Handler
       │ 1. Calculates total request latency (ms)
       │ 2. Emits single-line structured log to stdout
       │ 3. Returns headers: X-Correlation-ID, X-Request-ID
```

## 11. Mobile Request Tracing Contract

The Flutter mobile application participates in the distributed correlation model across all remote communications:

1. **Outbox Mutation Queuing:** When an offline action occurs (e.g. bookmarking or reading progress update), the local Drift database generates a unique `mutation_id` (UUID v4) and assigns an `initial_correlation_id`.
2. **Network Sync Execution:** When the `SyncEngine` flushes pending mutations to the remote API, it sets:
   - `X-Correlation-ID`: The mutation's `initial_correlation_id`.
   - `X-Client-Version`: Mobile app semantic version (`1.0.0+1`).
   - `X-Client-Platform`: `android` or `ios`.
3. **Retry & Backoff:** If the sync attempt encounters a transient network failure, the subsequent retry preserves the identical `initial_correlation_id`. This allows server logs to correlate repeated retry attempts with the original action.
4. **Response Reconciler:** Upon receiving the server response, the `SyncEngine` verifies the reflected `X-Correlation-ID` matches the active sync session before committing remote cursors.

#### 1. Liveness Probe (`/api/health/liveness`)
- **HTTP Method:** `GET`
- **Expected Status:** `200 OK`
- **Execution Target:** $< 5\text{ ms}$ execution time.
- **Dependencies:** None. Does not touch the database, disk, or network.
- **Payload:**
  ```json
  {
    "status": "UP",
    "timestamp": "2026-09-30T12:00:00.000Z"
  }
  ```

#### 2. Readiness Probe (`/api/health/readiness`)
- **HTTP Method:** `GET`
- **Expected Status:** `200 OK` (Ready) or `503 Service Unavailable` (Not ready).
- **Execution Target:** $< 100\text{ ms}$ execution time (timeout at 1500ms).
- **Dependencies:** Performs shallow SQL check (`SELECT 1;`) via Supabase client.
- **Payload (200 OK):**
  ```json
  {
    "status": "READY",
    "timestamp": "2026-09-30T12:00:00.000Z",
    "checks": {
      "database": "UP"
    }
  }
  ```
- **Payload (503 Service Unavailable):**
  ```json
  {
    "status": "UNREADY",
    "timestamp": "2026-09-30T12:00:00.000Z",
    "checks": {
      "database": "DOWN"
    },
    "reason": "Database connection refused"
  }
  ```

#### 3. Deep Health Check (`/api/health`)
- **HTTP Method:** `GET`
- **Expected Status:** `200 OK` or `503 Service Unavailable`.
- **Payload:**
  ```json
  {
    "status": "HEALTHY",
    "version": "1.0.0",

      }
    }
  }
  ```
- **Security Constraint:** Never expose database connection strings, user counts, server hostnames, or private environment variables in health responses.

## 13. Mobile Diagnostic Contract

Mobile errors and uncaught crashes must be handled with care to avoid transmitting personal devotional data while preserving diagnostic utility.

### Domain Exception Hierarchy Integration
The mobile error system expands upon `apps/mobile/lib/core/errors/app_exception.dart`:
- `DatabaseException`: Local SQLite / Drift operational failures.
- `EncryptionException`: SQLCipher key derivation or decryption errors.
- `ValidationException`: Input boundary violations (e.g. invalid Surah ID).
- `SyncException`: Outbox serialization or remote synchronization rejections.

### Mobile Crash Dump Contract (Local Ring Buffer)
Uncaught native or Flutter framework exceptions (`FlutterError.onError`, `PlatformDispatcher.instance.onError`) are captured into an encrypted local ring buffer (maximum 20 entries) on the device:

```dart
/// Architectural model for local mobile diagnostic snapshots
class LocalCrashReport {
  final String reportId;          // UUID v4
  final DateTime timestamp;        // ISO-8601 UTC
  final String appVersion;         // e.g. "1.0.0"
  final String buildNumber;        // e.g. "42"
  final String osVersion;          // e.g. "Android 14"
  final String errorCategory;      // e.g. "DATABASE"
  final String exceptionName;      // e.g. "DatabaseException"
  final String sanitizedMessage;   // e.g. "Failed to execute statement on encrypted table"
  final List<String> sanitizedStack; // Stripped of local device file paths
  final String? lastCorrelationId; // Correlation ID of last active network call
  final bool userOptedIn;          // Diagnostic sharing consent flag

  const LocalCrashReport({
    required this.reportId,
    required this.timestamp,
    required this.appVersion,
    required this.buildNumber,
    required this.osVersion,
    required this.errorCategory,
    required this.exceptionName,
    required this.sanitizedMessage,
    required this.sanitizedStack,
    this.lastCorrelationId,
    this.userOptedIn = false,
  });
}
```

### Privacy & Transmission Constraints
1. **Explicit User Consent:** Diagnostic reports are NEVER automatically transmitted to any server unless the user explicitly toggles "Share Anonymous Diagnostic Reports" in Settings.
2. **Local Inspection:** The user can inspect the exact plaintext contents of their local diagnostic log from the Settings screen before choosing to send it.
3. **No Devotional State:** The diagnostic payload contains zero information about which Surah was open, what Ayah was displayed, or what bookmarks exist.

All platform errors must resolve to one of 12 standard operational categories:

| Error Category | Subsystem / Context | Typical Scenario | HTTP Status | Alerting Level |
| :--- | :--- | :--- | :---: | :---: |

| **`DATABASE`** | PostgreSQL / Drift | Connection pool exhaustion, unique constraint violation, deadlocks. | `500 / 503` | ERROR / FATAL |

| **`SECURITY`** | Firewall / Rate Limiter | WAF block, excessive prayer calculation rate, secret injection attempt. | `429 / 403` | ERROR (Security alert) |
| **`RELEASE`** | CI/CD / Deployment | Hash mismatch in canonical content, build verification failure. | N/A | FATAL (Block release) |

## 20. Observability Failure-Mode Strategy

The core tenet of the observability architecture is: **The platform must never crash or degrade because observability failed.**

### Failure Protections
1. **Non-Blocking Telemetry:** All telemetry event emissions must be asynchronous and decoupled from the critical request-response path. Telemetry promises are never `await`ed in critical business loops.
2. **In-Memory Queue Boundaries:** The local telemetry dispatch queue must have a hard maximum cap (e.g. 500 events). If the queue fills (e.g. during an external network outage), incoming events are dropped silently without raising exceptions.
3. **Circuit Breaker:** If the telemetry reporting endpoint fails 5 consecutive times, a circuit breaker trips to `OPEN` for 60 seconds, disabling telemetry collection entirely to protect system resources.
4. **Graceful Logger Fallback:** If structured JSON serialization fails (e.g. due to circular references), the logger falls back to emitting a basic plaintext error message to `stderr`.
