## 3. LOAD STAGES & PEAK CONCURRENCY (1,000–5,000 VUs)

The test harness exercises the staging environment through four distinct load stages:

```text
       VU
      5000 +                     [Stage 3: Peak Spike]
           |                            / \
      2000 +               ____________/   \
           |              /                 \
       500 +  [Stage 1]  /                   \ [Stage 4]
           |    Warm-up /                     \ Cool-down
         0 +---+-------+-----------------------+----------+---> Time
              0m      1m                      4m         5m    6m
```

- **Stage 1 (Warm-Up — 1 min):** Ramp-up from 0 to 10% peak VUs (100–500 VUs) to prime connections and server caches.
- **Stage 2 (Sustained Baseline — 3 min):** Hold at 40% peak VUs (400–2,000 VUs) simulating standard daily usage.
- **Stage 3 (Peak Adhan Spike — 1 min):** Burst ramp-up to 100% peak VUs (1,000–5,000 VUs) simulating simultaneous worldwide prayer notifications.
- **Stage 4 (Controlled Ramp-Down — 1 min):** Ramp-down from peak to 0 VUs to observe graceful connection termination.

## 5. PASS / FAIL SLA THRESHOLDS

The staging run is evaluated against the following documented performance gates:

| Performance Metric | SLA Threshold | Rationale |
|---|---|---|
| **95th Percentile Latency (P95)** | `< 500 ms` | Ensures rapid responsive UI for 95% of worldwide worshippers |
| **99th Percentile Latency (P99)** | `< 1,000 ms` | Guards against extreme tail-latency spikes |
| **HTTP Error Rate** | `< 1.00%` | Unhandled 5xx server errors must remain below 1% (excluding expected 429 rate limits) |
| **System Stability** | Zero memory leaks | Server processes and connection pools must recover smoothly in Stage 4 |
