## 1. Executive Summary

During the execution of `supabase db push --linked` against the dedicated Supabase staging project (`mlxyegiwdzmcybvhtgwy`), migrations **01 through 06 applied successfully**. Execution halted abruptly at **Migration 07** (`20260923000003_hadith_collections_engine.sql`) with the PostgreSQL runtime error:

```text
ERROR: type "app_role" does not exist (SQLSTATE 42704)
```

This report details the read-only forensic audit conducted across all 17 migrations, repository source code, and database schema definitions.

**Key Finding:** The type `app_role` **does not exist anywhere in the repository or database schema**. It is never defined in any migration, table, schema, or extension. The database schema stores roles as `VARCHAR(30)` in `public.user_roles`, and `public.has_any_role` expects `VARCHAR[]`. The explicit type casts `'super_admin'::app_role` present in Migration 07 and Migration 08 are phantom casts that fail deterministically on any clean database.

## 5. Root Cause Analysis

### Why Did This Error Occur?
1. **Typo / Phantom Cast in Migration Authoring:**
   When authors wrote Migration 07 (`hadith_collections_engine`) and Migration 08 (`duas_adhkar_engine`), they inadvertently appended `::app_role` to `'super_admin'`. 
   
2. **Why Was It Never Detected Locally?**
   - Local verification suites relied on TypeScript mocks, in-memory repositories, and SQLite (Drift) for client testing.
   - Docker was not running locally, so Supabase local database (`supabase start`) had not executed these migrations against a live PostgreSQL parser.
   - The first time PostgreSQL's parser ever encountered statement 30 was when `supabase db push --linked` ran against the staging environment.

### Clean-Install Reproducibility:
**This failure is 100% reproducible on EVERY clean installation.** Any fresh PostgreSQL database executing the repository's 17 migrations in sequence will fail on Migration 07 at statement 30.

## 6. Recommended Minimal Remediation Strategy

There are two potential technical solutions to resolve this issue. Their trade-offs are analyzed below:

### Option A: Clean Correction of Phantom Cast in Migrations 07 & 08 (RECOMMENDED)
- **Action:** In `20260923000003_hadith_collections_engine.sql` and `20260923000004_duas_adhkar_engine.sql`, replace `'super_admin'::app_role` with `'super_admin'`.
- **Rationale:** 
  - Aligns Migration 07 and 08 with the rest of the codebase (Migrations 01, 02, 03, 05, 06, 10, 14).
  - Perfectly matches the function signature `has_any_role(lookup_uid UUID, check_roles VARCHAR[])`.
  - Migrations 07 and 08 have **not** been applied to staging yet, so no remote migration history is broken or modified. Migrations 01–06 remain completely untouched.
  - Leaves the schema clean, avoiding unnecessary custom types/domains.

### Option B: Additive Type / Domain Creation Prior to Migration 07
- **Action:** Create a domain or enum `app_role` before Migration 07 executes:
  `CREATE DOMAIN public.app_role AS VARCHAR(30);`
- **Drawback:** Requires inserting a migration between Migration 06 and Migration 07 or defining an unused type that no other migration or table in the schema uses. Furthermore, if created as an enum, it would conflict with `has_any_role` taking `VARCHAR[]`.
