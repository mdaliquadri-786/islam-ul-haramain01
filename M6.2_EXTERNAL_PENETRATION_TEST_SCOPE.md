## 1. PURPOSE & MANDATE

Before public release to millions of global Muslims, **ISLAM UL HARAMAIN** mandates an independent, objective external penetration test conducted by an accredited cybersecurity firm (CREST, OSCP, OSCE, or CHECK certified).

This document establishes the authoritative boundaries, attack surface inventory, testing modalities, out-of-scope targets, test accounts, rules of engagement, emergency protocols, and reporting criteria for the external engagement.

## 3. STRICTLY OUT-OF-SCOPE TARGETS & PROHIBITIONS

> [!CAUTION]
> Testing activities targeting the following components or methods are strictly forbidden:

1. **Volumetric Denial of Service (DoS/DDoS):** Volumetric network flood attacks (SYN flood, UDP flood, DNS amplification) against cloud providers (Vercel, Supabase, Cloudflare, AWS) are strictly prohibited. Application-layer algorithmic DoS must be demonstrated with single/low-volume requests proving high complexity without degrading environment availability.
2. **Canonical Religious Content Modification:** Any attempt to alter canonical scripture text (Quran, Hadith, Duas) in source control or production-bound datasets.
3. **Production Cloud Environments:** No tests may target production systems, production databases, production DNS, or real live user accounts.
4. **Third-Party External Services:** Attacks directed against external audio CDNs, Google Play infrastructure, Apple App Store servers, or upstream DNS root servers.
5. **Social Engineering & Phishing:** Spear-phishing, credential harvesting campaigns, or social engineering targeting platform engineers, scholars, or community board members.
6. **Physical Facility Attacks:** Physical intrusion attempts against data centers, developer offices, or residences.
7. **Destructive Database Drops:** Issuing `DROP DATABASE`, `TRUNCATE` on canonical seed tables, or destructive actions that wipe staging infrastructure.

## 5. RULES OF ENGAGEMENT & OPERATIONAL PROTOCOLS

1. **Written Authorization Mandate:** No testing may begin without a formally countersigned Statement of Work (SOW) and Letter of Authorization (LoA) signed by platform leadership.
2. **Dedicated Staging Environment:** Testing is strictly confined to the dedicated staging environment (`staging.islamic-platform.org` and linked staging Supabase instance).
3. **Identification Header:** All HTTP requests from the testing team must include the custom header:
   ```http
   X-PenTest-Authorization: Haramain-SecAudit-M6.2
   ```
4. **Testing Window:** Testing will be authorized 24/7 during an agreed 14-calendar-day testing sprint.
5. **Emergency Contact Placeholders:**
   - **Primary Technical Contact:** `[Lead Security Engineer — security@islamic-platform.org / Phone Placeholder]`
   - **Infrastructure Operations:** `[Lead DevOps Architect — devops@islamic-platform.org / Phone Placeholder]`
   - **Executive Escalation:** `[Project Director — director@islamic-platform.org / Phone Placeholder]`
6. **Critical Vulnerability Immediate Escalation Protocol:**
   If a Critical vulnerability (CVSS v3.1 >= 9.0) is identified—such as unauthenticated RLS bypass, remote code execution (RCE), full database dump capability, or theological text defacement—the tester must halt further testing on that vector and notify the Primary Technical Contact within **2 hours**.
7. **Data Handling & Responsible Disclosure:**
   - All vulnerability data, transcripts, and proof-of-concept scripts must be encrypted using PGP/GPG in transit and at rest.
   - Zero disclosure to external parties, public forums, or social media prior to formal platform release and patching.
   - All synthetic test data must be documented and cleanly purged upon engagement conclusion.

## 6. DELIVERABLES & REPORTING CRITERIA

The testing firm must deliver a formal **Penetration Test Report** within 5 business days of testing completion containing:
1. **Executive Summary:** High-level summary of security posture suitable for platform leadership and the Scholar Advisory Board.
2. **Methodology Overview:** Detailed breakdown of tools, techniques, and testing modalities used.
3. **Vulnerability Findings Catalog:**
   - Vulnerability Title & Unique Finding ID
   - Severity Rating (CVSS v3.1 Base Score & Vector String)
   - Affected Asset / URL / Route / Line of Code
   - Technical Vulnerability Description & Root Cause
   - Step-by-Step Proof of Concept (PoC) with raw HTTP request/response evidence
   - Remediation Recommendations conforming to platform architecture
4. **Remediation Re-Test Verification:** Free re-testing of remediated findings within 30 days of initial report delivery.
