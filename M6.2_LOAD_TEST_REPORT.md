## 3. PART B: STAGING & CLOUD LOAD TESTING REQUIREMENTS (EXTERNAL PREREQUISITE)

> [!IMPORTANT]
> Local microbenchmarks validate algorithmic throughput in a single CPU process. They do **NOT** prove cloud infrastructure scalability, database connection pooling resilience, or network latency profiles under distributed concurrency.

### 3.1 Behaviors Requiring Live Cloud Infrastructure Testing
The following factors cannot be evaluated in a local offline environment and require a live staging deployment:
1. **Concurrent HTTP Network Traffic:** Testing TCP socket reuse, TLS 1.3 handshakes, and HTTP/2 multiplexing across geographically dispersed clients.
2. **Authenticated JWT Session Overhead:** Supabase Auth JWT token parsing and signature verification under 1,000+ concurrent requests/second.
3. **API Route Execution under Concurrency:** 27 REST route handlers processing concurrent JSON payloads on edge/server runtimes.
4. **Supabase PostgreSQL & Connection Pooling:** PgBouncer connection allocation under high concurrent query loads, transaction isolation, and query queueing.
5. **Row-Level Security (RLS) Under Load:** Database CPU consumption and latency impact when evaluating `auth.uid() = user_id` policies across thousands of simultaneous queries.
6. **Distributed Rate Limiting:** Verifying rate limit counters across multiple server instances (e.g., Cloudflare Rate Limiting or Redis) rather than single-process memory.
7. **CDN Edge Caching Hit Ratios:** Cache-hit efficiency on static Quran/Hadith routes and audio reciter catalogs.
8. **Resource Saturation & Lock Contention:** Database IOPS, memory utilization, and WAL write throughput during peak bursts.

### 3.2 Executable Staging Load Testing Plan (k6)
An executable, production-ready k6 load testing script has been provisioned at:
`scripts/staging-load-test.js`

**Test Execution Command (on Staging Runner):**

**Target Load Stages Defined in Harness:**
1. **Stage 1: Warm-up (1 min):** Ramp-up from 0 to 50 Virtual Users (VU).
2. **Stage 2: Sustained Load (3 min):** 200 concurrent VUs generating steady API traffic (Health, Prayer Times, Search, Reciters).
3. **Stage 3: Peak Adhan Spike (1 min):** Burst ramp-up to 500 VUs simulating worldwide prayer notification checks.
4. **Stage 4: Cool-down (1 min):** Ramp-down from 500 to 0 VUs.

**Pass/Fail SLA Thresholds:**
- `http_req_duration (P95)`: < 500 ms
- `http_req_duration (P99)`: < 1000 ms
- `HTTP Error Rate (4xx / 5xx)`: < 1.00% (excluding expected 429 rate limits)
