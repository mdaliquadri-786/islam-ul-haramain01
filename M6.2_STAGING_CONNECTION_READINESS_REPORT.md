### Key Differences & Compatibility Architecture:
1. **Supabase New API Key Format vs Legacy JWTs:**
   - Older Supabase projects generated signed JWTs starting with `eyJ...` for `anon` and `service_role`.
   - Newer projects utilize `sb_publishable_...` for client access and `sb_secret_...` for server administration.
   - The Supabase client libraries (`@supabase/ssr` 0.5.2 and `@supabase/supabase-js` 2.49.1) natively support both formats when passed to client constructors.
   - To ensure zero developer friction, `@islamic/database` (`packages/database/src/client.ts`) was non-destructively updated to accept `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` as a fallback if `NEXT_PUBLIC_SUPABASE_ANON_KEY` is not set.

2. **`ADMIN_API_SECRET` Independence:**
   - `ADMIN_API_SECRET` is strictly an internal application secret evaluated in `apps/web/src/lib/admin-auth.ts`.
   - It is **never** the Supabase database password or service role key.
   - Administrators should generate a standalone 256-bit random hex string (e.g., via `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"`) and keep it private.
